# Plan: vajra-bm25 0.5.1 implementation

Implements the five Vajra problems from the Verity benchmark (17 Nov 2026, vajra-bm25 0.5.0, §9) as a
bug-fix release with no API breaks. Source documents: `references/Vajra BM25 — Plan Patches, Roadmap and
Where to Play.md` (the release plan) and `references/Verity Search and Agents Benchmark ).pdf`.
Baseline to compare against: `results/baseline-0.5.0/BASELINE.md`.

This file expands the release plan with the decisions the code review turned up. It does not replace it.

## Where the repo differs from the release plan

| Plan says | Repo has | Decision |
|---|---|---|
| `setup_logging()` stays as the opt-in | The function is `configure_logging()`; there is no `setup_logging` | Keep `configure_logging()` as the opt-in. No alias: the CLI prints through its own console and does not need library logs |
| Add `add_documents(list)` | `batch_add_documents(list)` already exists | Add `add_documents` as the public name; keep `batch_add_documents` as an alias |
| Duplicate check "keep an ID set on the corpus" | `DocumentCorpus` already has an id index (`_index`, used by `get`) | Use `corpus.get(doc.id)`; no new structure |
| `VectorizedIndexSparse.build` is the only `Pool` | The dense `VectorizedIndex.build` already tokenises in-process | Only the sparse index changes pool behaviour; both builders take the analyzer |
| SciFact NDCG@10 "within 0.001 of 0.675" | This repo's harness gives 0.670 (README says 0.670); 0.6753 is Verity's harness | Acceptance is identical to the 0.5.0 baseline in this harness: nDCG 67.0, recall 78.9 |
| Persistence not mentioned | `save_index`/`load_index` rebuild scorers separately and would drop an analyzer | Persist `analyzer` in the index file; old files load with the default |
| Not mentioned | In hybrid/vector mode the lazily built vector engine never sees documents added later (same bug class as fix 1) | Sync the vector engine on add; reset it on remove |

## Fix 1: stale scorers after add/remove

`VajraSearchOptimized` gets one `_build_scorers()` that creates `scorer`, `maxscore_scorer`,
`numba_scorer` and `eager_scorer` from `self.index` plus the flags (`k1`, `b`, `use_maxscore`,
`use_numba`, `use_eager`). It is called from `__init__`, `load_index`, and a new `_rebuild_index()` that
`add_document`, `remove_document` and `add_documents` share. The index type (dense or sparse) is kept
across rebuilds. Today `add_document`/`remove_document` rebuild only `self.scorer`, so the eager scorer
(the default path on sparse indices) keeps answering from the old matrix.

Tests (every scorer path, not just the default): add a document and find its unique term with each of
eager, numba, maxscore and the traditional scorer, on a sparse index; the same on a dense index; remove a
document and confirm it is gone; `add_documents` of a batch costs one rebuild; duplicate add raises;
Verity's "gamma" reproduction.

## Fix 2: no `multiprocessing.Pool` by default

`VectorizedIndexSparse.build(corpus, analyzer=None, n_jobs=1)` tokenises in-process. A pool is used only
when `n_jobs > 1` and the corpus has 20,000+ documents, and it is a `spawn` context (safe in threaded
servers). `n_jobs=-1` means all cores. `VajraSearchOptimized` and `VajraSearchParallel` accept `n_jobs`.

Trade-off to measure, not assume: for large corpora the old default used all cores, so the new default
makes a 1M-document build slower unless `n_jobs` is passed. The 0.5.1 benchmark run records both
`n_jobs=1` and `n_jobs=all cores` at 200k and 1M. The 20,000 threshold is a starting value; the 200k
corpus is where to check it.

Tests: building 629 documents starts no child processes; the pool path (`n_jobs=2`, a small threshold
patched in) gives an index identical to the in-process one; timing against 0.5.0 on 629 and 5,183 docs.

## Fix 3: analyzer hook and `tag_aware_analyzer`

`analyzer: Callable[[str], List[str]]`, default `preprocess_text`, on `VajraSearchOptimized`,
`VajraSearchParallel`, `VectorizedIndex.build` and `VectorizedIndexSparse.build`. It is applied to
`title + " " + content` when indexing and to the query when searching, so both sides always agree. The
base `VajraSearch` is out of scope (the release plan names the optimized engine and the index builders).
With a process pool the analyzer must be picklable (a module-level function), and the same holds for
`save_index`, which stores it; a lambda raises a clear error at save time.

`tag_aware_analyzer(text)` = `preprocess_text(text)` followed by joined forms of hyphenated alphanumeric
identifiers that contain a digit: `V-110` adds `v110` (the default tokens `v` and `110` stay);
`P-400A/B` adds `p400a` and `p400b`; `DNV-ST-F101` adds `dnvstf101`. Dates (`2026-11-19`) and plain
hyphenated words (`state-of-the-art`) add nothing. A bare `V110` in a query then matches `V-110` in a
document, because both reduce to `v110`.

Tests: default analyzer output identical to `preprocess_text` and SciFact identical to the baseline;
with `tag_aware_analyzer`, "V-110" ranks the V-110 passage first on a fixture where "pressure" repeats;
custom analyzer is used for documents and queries; save/load round-trips the analyzer.

## Fix 4: logging

`logging_config.py`: on import add only a `NullHandler` to the `vajra_bm25` logger; no level, propagation
left on. `configure_logging()` stays and still installs the stdout handler with `propagate = False`, so
the CLI or a script can opt in. Test: with a handler on the root logger, one Vajra message arrives once.

## Fix 5: `__version__`

`importlib.metadata.version("vajra-bm25")`, falling back to `"0+unknown"` when running from a source
tree that is not installed. `pyproject.toml` becomes 0.5.1. The editable install keeps its old metadata
until it is reinstalled (`uv pip install -e .`), so the test needs the reinstall.

## Vector sync (added to fix 1)

After `add_document` or `add_documents`, if the lazy vector engine exists, the new documents are added
to it. After `remove_document` the vector engine is reset so it rebuilds on next use. Test with a fake
vector engine; no model download.

## Release steps

1. `pytest tests/` passes (baseline: 312) plus the new tests.
2. Reinstall editable, check `vajra_bm25.__version__ == "0.5.1"`.
3. SciFact lexical and hybrid reruns with `TAG=after-0.5.1`; compare with `summarize_hybrid.py` and the
   baseline JSON. Default-analyzer results must be identical.
4. `CHANGELOG.md` entry naming each Verity finding; update `CLAUDE.md` (version, test count).
5. Tag `v0.5.1`, build, publish to PyPI, send Verity the upgrade note. Steps 4 to 5 need the owner's go-ahead.

## Not in 0.5.1

Stemming, synonyms (the "How heavy is the crude oil?" regression), metadata filters, incremental index
updates, dropping SciPy, the rarity-weighted keep test (it lives in Verity), hybrid default tuning and
fusion depth. These change results or packaging and are listed in `results/baseline-0.5.0/BASELINE.md`
as 0.6 inputs.
